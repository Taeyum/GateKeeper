# 화면 세션 리뷰 (feat/web)

리뷰어가 쓴다. main의 docs/handoff/feedback.md와 머지 충돌이 나지 않게 화면 세션 리뷰는 이 파일에만 적는다.

## API 계약 초안과 8단계 계획 리뷰

결과: L1~L4 반영 후 계약 확정. 엔드포인트별 JSON 예시, 상태(status)와 권고(verdict)를 나눈 것, nodes 배열, 건너뜀 규칙 표, replay, 오류 응답 통일, approver를 헤더에서만 채우는 것이 좋다.

### 열린 질문 9개 결정
| # | 결정 |
|---|---|
| 1 has_similar_incident | 그대로. 정의는 "같은 서비스 + 같은 유형 + outcome 장애"(history.bump)다. 목업도 이 정의로 계산한다(계획의 "outcome == 장애만" 계산을 고친다). v0/v1은 항상 false |
| 2 자동 승인 기록 | 그대로 (`GET /api/approvals?status=auto_approved`) |
| 3 replay | 그대로. 단 이벤트 기록은 서버 메모리라 재시작 뒤에는 없다. 재시작 뒤 스트림에 연결하면 서버가 체크포인터 상태로 현재 종료 이벤트(awaiting_approval 또는 done) 하나를 보내고 닫는다는 줄을 계약에 더한다 |
| 4 건너뜀 시점 | 그대로(awaiting_approval 포함). 더해서 `error`로 끝났을 때 시작 안 한 노드는 "건너뜀"이 아니라 "진행 안 됨"으로 표시한다 |
| 5 퍼센트 인코딩 | 그대로 |
| 6 impact id, name | 그대로 |
| 7 suggested 형식 | 그대로 |
| 8 요청자 조회 범위 | 그대로(데모), 계약에 "실서비스는 소유자 확인" 한 줄 유지 |
| 9 재요청 | **바꾼다.** 같은 request_id를 다시 쓰지 않고 새 요청으로 만든다: `POST /api/requests`에 선택 필드 `parent_request_id`. 응답은 새 request_id. 상세 응답에 `parent_request_id`(없으면 null)를 더한다. 이유: 같은 thread를 다시 돌리면 errors(operator.add)와 metrics가 이전 실행 위에 쌓이고, 감사 기록과 결재함에서 1차 요청과 재요청이 한 건으로 섞인다. 서버는 부모의 마스킹 본문과 새 본문을 합쳐 parse_request에 넣는다 |

### L1. "내 요청" 목록 경로가 없다 (필수)
- 디자인 1번 화면에 "내 요청" 목록이 있는데 계약에 목록 경로가 없다.
- 반영: `GET /api/requests`(role 필수). requester면 X-User-Name이 같은 요청만, approver면 전부. 최신순. 항목 모양은 `/api/approvals` 항목과 같고(`status` 포함), `parent_request_id`를 더한다.

### L2. 서브그래프 내부 노드는 이벤트로 보내지 않는다 (필수)
- 5단계 리뷰(K1)로 policy_agent, impact_agent, history_agent가 컴파일된 서브그래프가 된다. LangGraph 이벤트에는 내부 노드(check_policy, read_rules, write_notes 등)도 나온다.
- 반영: 계약 "규칙"에 "SSE와 nodes에는 SPEC 3장의 최상위 노드 9개만 나온다. 서브그래프 내부 노드는 보내지 않는다"를 적는다.

### L3. 수동 검토 전환의 이벤트를 하나로 정한다 (필수)
- 지금은 `error` 이벤트와 `done(status=manual_review)`가 둘 다 수동 검토를 뜻할 수 있다.
- 반영: 예상한 검토 불가(ReviewIncomplete: 정책 검사 확인 불가, 대상 없음)는 `done`(status `manual_review`, `message` 포함)으로, 예상 못 한 서버 오류만 `error`로 보낸다. 둘 다 상태는 manual_review이고 화면 문구는 같아도 된다.

### L4. 규정 문구 두 줄 고치기 (필수)
- CHG-05는 "알림"이 아니라 "요청 시점" 규정이다: "핵심 서비스는 작업 24시간 전까지 요청해야 해요."
- CHG-03은 외부 노출만 막는다: "DB 포트는 외부에 열 수 없어요. 등록된 파트너 IP 1개(/32)만 예외예요."

### 참고
- 쉬운 문구의 숫자(30일, 24시간)는 화면에 고정된 규정 값이다. 데모에서는 괜찮지만 보고서 한계에 "규정 값이 바뀌면 화면 문구도 고쳐야 함"을 적는다.
- 확정한 계약 커밋을 main으로 가져갈 때 7단계 프롬프트 항목 4(재요청)는 "parent_request_id로 새 요청을 만든다"로 바꿔 넣는다.

## 8단계 결과 리뷰 (화면)

결과: 좋음. 리뷰어가 목업으로 직접 띄워 1440px/390px에서 작성, 진행(병렬 3갈래), 반려 결과("지금 → 이렇게" 3묶음), 결재함 상세, 표준 변경 자동 승인을 확인했다. 결재 업무 화면으로 읽히고 Base 채팅 화면과 겹치지 않는다. 판정 배지는 색과 글자를 같이 쓰고, 좁은 화면에서도 깨지지 않는다.

### M1. 자동 승인 결과의 배지 중복 (작은 수정)
- 결과 카드에 "자동 승인" 배지가 위(큰 배지)와 아래(작은 칩)에 두 번 나온다. 아래 칩을 빼거나 "표준 변경 STD-01" 같은 다른 정보로 바꾼다.

### 참고
- 목업은 입력 문장을 키워드로 dev 시나리오에 맞춰서, 다른 날짜를 써도 "이렇게 이해했어요"에는 dev 라벨 값(예: 10/30 16시)이 나온다. 목업으로 시연할 때는 dev 문장을 그대로 쓴다. 실제 백엔드에 붙이면 사라지는 문제다.
