## 리허설 (2026-10-22, 실제 서버)

자세한 표는 `docs/DEMO.md` 3장에 있다. 시연 문장 검토는 30.9초와 21.7초, 표준 변경 자동 승인은 20.4초였고 브라우저 콘솔 오류는 0건이었다. **문서와 달랐던 것 세 가지**:

1. "이 내용으로 다시 요청하기"는 다시 반려된다. 보내는 문장의 접속할 곳이 "등록된 파트너 IP"라는 문구라 엔진이 출발지를 못 읽는다(고칠 것이 3개에서 1개로 줄어든다). 목업은 승인으로 끝나서 실제와 달랐다. "직접 고쳐 쓰기"로 파트너 IP를 적으면 승인이 나온다.
2. 작업 시각이 없는 표준 변경은 자동 승인되지 않고 조건부 승인이 나온다(시각이 없으면 동결을 확인할 수 없는 fail-safe). 시연 문장에 "내일 오후 3시"를 넣었다.
3. 반려를 권고한 요청을 승인하려면 사유가 필요하다.

리허설 스크립트는 저장소 밖에서 돌렸고(커밋하지 않음) 리허설용 체크포인터와 감사 로그 경로를 따로 줘서 기존 `.data` 데이터를 건드리지 않았다. 리허설에서 Anthropic에 보낸 요청은 총 9건(첫 서버 3건, 두 번째 서버의 시드 3건과 시연 3건)이고, 9단계의 요청당 비용(v2 0.068 USD)으로 어림하면 0.5 USD 안팎이다(측정하지는 않은 추정).

## 핵심 코드 설명 (발표용)

이번 단계는 코드를 바꾸지 않았다. 설계 판단만 적는다.

- **보고서는 측정 파일과 대조해 고친다.** 보고서의 숫자와 문장이 summary와 RESULTS.md와 같아야 읽는 사람이 믿는다. 숫자는 그대로였고, 인과를 단정한 문장(오탐 원인, 대안 품질 하락의 이유)만 "추정"이나 "분석 안 함"으로 낮췄다. 정답 파일을 열지 않는 규칙 때문에 사례 단위 원인을 단정할 수 없다.
- **시연은 목업이 아니라 실제 서버로 리허설한다.** 목업은 승인으로 끝나는 재요청이 실제 서버에서는 다시 반려된다는 것을 숨겼다. 발표 때 처음 마주치는 것을 미리 찾으려는 것이다. 찾은 것은 숨기지 않고 시연 순서(직접 고쳐 쓰기)와 향후 개선 후보에 넣었다.
- **공개 저장소 점검은 내용을 출력하지 않는다.** 키 패턴이 걸리면 값 자체가 로그에 남을 수 있어서 파일 이름과 개수만 보고, 걸린 한 건은 앞 8자와 뒤 2자로 가짜 값인지만 판정했다.
