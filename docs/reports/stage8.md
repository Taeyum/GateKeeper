# 8단계 보고: 화면 (백엔드와 병렬, feat/web)

## 한 줄 요약

백엔드(5~7단계) 없이 `docs/API_CONTRACT.md`(확정)를 따르는 Vite 목업 위에 Vue 3 화면 4개(요청자 작성, 진행, 결과, 승인자 결재함)를 만들고 브라우저로 끝까지 확인했다. 타입 검사, 단위 테스트 88개(8파일), 프로덕션 빌드가 통과한다. 실제 API 연결은 7단계 뒤에 확인한다.

## 결과

| 항목 | 결과 |
|---|---|
| `npm run typecheck` (vue-tsc) | 통과 |
| `npm test` (Vitest) | 8파일 88개 통과 |
| `npm run build` | 통과 |
| 목업 서버 curl 확인 | 요청 접수, 스트림 재생과 실시간, 상세, 결재함 두 목록, 결정(200/409/403), 검증(422), 헤더 없음(403) |
| 브라우저 확인(목업) | 아래 "시연 순서" 전체를 실제 브라우저로 따라가 봄. 스크린샷 파일은 커밋하지 않았다 |
| `app/`, `tests/`, `docs/PROGRESS.md` | 수정하지 않았다 |

## 만든 것

- `web/`: Vue 3 + Vite 8 + TypeScript + Vue Router 5 + Vitest 5. `sh/run_web.sh`로 띄운다.
- 화면: 작성(유형별 안내, 내 요청 목록, 고쳐 쓰기), 요청(실시간 8단계 타임라인, "이렇게 이해했어요", 결과: 쉬운 묶음의 고치기 안내와 "지금 -> 이렇게", 자세한 근거, 비슷한 사고, 처리 상태, 다시 요청), 결재함(탭, 위험도 순 목록, 상세, 승인/반려와 사유).
- 목업(`web/mock/`): dev 요청 10건과 CMDB/캘린더/이력/장애 티켓 데이터로 계약 그대로 응답한다. 근거 문장은 규칙 엔진을 한 번 돌려 얻은 실제 문장을 고정했다(`evidence.json`).

## 시연 순서

```bash
VITE_API_MOCK=1 bash sh/run_web.sh      # http://127.0.0.1:5173
```

1. 요청자 김운영으로 아래 문장을 입력하고 "검토 요청하기": `10월 30일 금요일 저녁 8시에 payments-db 방화벽 좀 열어주세요. 외부 파트너사가 접속해야 해요.` ("이번 주 금요일"은 접수일 기준이라 접수일에 따라 동결에 안 걸리므로 날짜를 적는다. 목업은 `payments-db`가 들어 있으면 REQ-D01로 인식하므로 이 문장도 같은 시나리오다)
2. 진행 화면: 앞의 두 단계가 끝나면 규정 확인 / 영향 확인 / 사고 사례 확인 세 갈래가 동시에 돌고 결과 정리, 내용 점검, 승인자 결재로 이어진다. "이렇게 이해했어요"에서 접속할 곳과 열어 둘 기간에 "빠졌어요"가 보인다.
3. 결과 화면: "이대로는 승인되기 어려워요", 고쳐야 할 3가지(작업 시간 / 접속할 곳 / 열어 둘 기간)와 "지금 -> 이렇게", 비슷한 사고. "자세한 근거 보기"에서 규정 번호와 엔진 문장을 본다.
4. "이 내용으로 다시 요청하기": 새 요청이 만들어지고(부모 요청과 연결) 이번에는 승인 권고가 나온다.
5. 상단에서 승인자 박CAB으로 전환: 결재함 맨 위가 가장 위험한 요청이다. 상세를 보고 "승인하기"를 사유 없이 눌러 보면(반려 권고를 승인하는 경우) 사유를 적으라는 안내가 나온다. 사유를 적고 "반려하기".
6. 요청자로 돌아가 "내 요청"에서 그 요청을 열면 "반려됐어요"와 승인자의 코멘트가 보인다.
7. 자동 승인: `auth-service 로그 레벨을 INFO에서 DEBUG로 올릴게요. 재시작은 없어요.` 를 보내면 영향 확인과 사고 사례 확인이 "건너뜀"으로 보이고 "자동으로 승인됐어요"가 나온다. 승인자 화면의 "자동 승인 기록" 탭에도 쌓인다.
8. 예외 시연(문장 뒤에 붙이는 목업 전용 표시): `[목업:수동검토]`는 규정 확인이 "확인 못 했어요"로 끝나 나머지가 "진행 안 됨"이 되고 수동 검토 안내가 나온다. `[목업:영향도실패]`는 영향도만 확인하지 못하고 검토는 계속된다. 대상 서비스를 못 찾는 문장은 처음 단계에서 수동 검토로 넘어간다.
9. 스트림 끊김 복구: `VITE_API_MOCK=1 VITE_MOCK_DROP=1 bash sh/run_web.sh`. 요청마다 첫 연결을 세 번째 이벤트 뒤에 끊는데, 화면이 "연결이 잠시 끊겨서 다시 연결하고 있어요"를 보이고 상태를 다시 읽어 이어 받는다. `VITE_MOCK_SPEED=0.2`로 5배 빠르게 볼 수 있다.

## 핵심 코드 설명 (발표용)

- **건너뜀은 서버가 아니라 화면이 계산한다** (`web/src/lib/review.ts`의 `timelineSteps`). 서버는 실행한 노드의 이벤트만 보내므로 표준 변경이나 v1처럼 경로가 달라져도 계약을 바꾸지 않는다. 시작 기록이 없는 노드는 정상 종료면 "건너뜀", 수동 검토로 끝났으면 "진행 안 됨"으로 가른다. 거기까지 가지 못한 것을 건너뛴 것처럼 보이지 않게 하려는 것이다.
- **실행과 화면 연결을 분리했다** (`web/src/lib/flow.ts`의 `RequestFlow`). SPEC 6장대로 그래프 실행은 SSE와 무관하게 계속되므로, 연결이 끊기면 `GET /api/requests/{id}`로 상태를 복구하고 서버의 replay로 이어 받는다. 서버가 보낸 `error` 이벤트와 연결 오류가 같은 이름이라 `data` 유무로 구분한다.
- **판정은 코드, 설명은 읽기 쉽게** (`web/src/copy/rules.ts`). 규정 번호를 쉬운 문구와 묶음으로 바꾸는 표를 화면에 두고, 엔진이 만든 근거 문장은 "자세한 근거"에 그대로 보여 준다. 사용자는 "무엇을 고치면 되는지"를 먼저 보고, 감사나 문의에 필요한 규정 번호와 원문 근거는 접어서 남긴다.
- **목업이 계약 그대로다** (`web/mock/engine.ts`). 시나리오, 이벤트 순서, 목록 정렬이 계약과 같고 단위 테스트가 고정하므로, 7단계 백엔드가 같은 계약을 따르면 화면 수정이 거의 없다.

## 계획과 달라진 점

- 테스트를 별도 커밋(계획의 8번)으로 몰지 않고 기능과 같은 커밋에 넣었다(`tests/`: client, session, mock, format, rules, review, flow, decision).
- 개발 서버가 `/api`를 보내는 기본 주소는 `http://127.0.0.1:8100`이다. 프롬프트에는 8000이라고 했지만 `sh/run_api.sh`의 기본 포트(`GK_API_PORT`)가 8100이라 맞췄다. `GK_API_URL`로 바꿀 수 있다.
- 목업의 "시스템 설명"은 쉬운 말로 손으로 쓴 문장(`web/mock/explanations.json`)이다. 정답 라벨의 rationale은 규정 번호가 섞인 문장체라 승인자 화면에서 읽기 어려워서다.
- 승인자 목록 선택, 탭은 주소(`?selected=`, `?tab=auto`)에 담는다. 역할이 맞지 않는 화면을 열면 화면 대신 "승인자 박CAB 역할로 볼 수 있어요" 전환 안내가 나온다.

## 7단계와 메인 세션에 알릴 것

- 백엔드가 따라야 할 계약은 `docs/API_CONTRACT.md`다. 화면이 기대는 것: 재요청은 `parent_request_id`로 새 요청, 연결 시 지난 이벤트 replay, 서버 재시작 뒤에는 종료 이벤트 하나, `X-User-Name`은 퍼센트 인코딩, `GET /api/requests`, `GET /api/approvals?status=auto_approved`, 수동 검토는 `done`(`manual_review` + `message`)과 예상 못 한 오류만 `error`, SSE와 `nodes`에는 최상위 노드 9개만, `has_similar_incident`는 "같은 서비스 + 같은 유형 + 장애".
- `Recommendation.explanation`은 승인자 화면의 "시스템 설명"에 그대로 나온다. 5단계 설명 프롬프트가 규정 번호와 영어 약어 없이 쉬운 한국어로 쓰게 하면 화면이 가장 읽기 쉽다(목업은 그렇게 가정했다).
- 재요청의 `text`: 계약은 "마스킹한 본문"이라고만 한다. 목업은 새로 쓴 본문만 돌려주는데, 서버가 부모 본문과 합친 것을 돌려주면 "내가 쓴 내용"에 둘이 함께 보인다. 어느 쪽이든 화면은 동작하지만 7단계에서 정하면 좋다.
- main으로 가져올 때: 계약 커밋 `747464c`만 가져오고, PROMPTS.md 7단계의 재요청 항목은 "`parent_request_id`로 새 요청을 만든다"로 바꿔 넣는다.

## 리뷰 반영

- M1 자동 승인 결과에 "자동 승인" 배지가 위(큰 배지)와 아래(칩)에 두 번 나오던 것: 아래 상태 칩을 숨기고 그 자리에 "종류: 표준 변경 (로그 레벨 변경)"을 보여 준다. 숨길지 정하는 규칙은 `showStatusChip`(`web/src/lib/presentation.ts`)이고 테스트가 있다. 권고(승인 권고)와 처리 상태(승인자 확인 중, 승인됨)는 서로 다른 정보라 자동 승인만 숨긴다.
- M2 한글 입력 조합 중에는 v-model이 갱신되지 않아 입력 직후 첫 클릭이 비활성 버튼에 먹히던 것: 요청 입력창과 결정 사유 칸을 `:value` + `@input`으로 바꿔 조합 중에도 값을 바로 받고, 제출 버튼은 비활성으로 두지 않고 누르는 순간 입력창의 현재 값으로 빈 입력을 다시 검사한다(빈 입력이면 "변경 내용을 적어 주세요."를 보이고 입력창으로 돌아간다). 결정 사유도 누르는 순간 현재 값을 읽어 "권고와 다른 결정의 사유" 검사에 쓴다.
  - 재현과 확인: 브라우저에서 `compositionstart`를 보내고 `compositionend` 없이 `input`(isComposing)만 보내 조합 중을 흉내 냈다. 고치기 전에는 입력창에 글자가 있는데 버튼이 비활성이고 클릭해도 넘어가지 않았다. 고친 뒤에는 버튼이 활성이고 첫 클릭으로 제출된다. 결정 사유도 조합 중에 쓴 문장이 그대로 저장되고, 사유 없이 반려 권고를 승인하면 안내가 나온다. 실제 한글 IME로 직접 타이핑한 확인은 아니며(자동화 브라우저는 IME 조합을 만들지 못한다), 자동 테스트는 없다(컴포넌트 테스트 환경이 없다).
- K5(메인 세션 5단계): 승인자 화면의 "시스템 설명"에 백엔드 LLM의 `explanation`이 그대로 나오므로 decide 프롬프트가 규정 번호 없이 "~해요"체로 쓰게 하는 일은 메인 세션이 맡는다. 화면 세션에서는 바꿀 것이 없다.

## 목업으로 시연할 때 주의

목업은 입력 문장을 키워드로 dev 예시 중 하나에 맞춘다. 그래서 문장에 다른 날짜를 써도 "이렇게 이해했어요"에는 dev 예시의 값(예: 10/30 오후 8시)이 나온다. 목업으로 시연할 때는 위 시연 순서의 dev 문장을 그대로 쓴다. 실제 백엔드에 붙이면 사라지는 문제다.

## 한계

- 쉬운 문구의 숫자(30일, 24시간)는 화면에 고정된 규정 값이다. 규정(`rules.json`)이 바뀌면 `web/src/copy/rules.ts`도 고쳐야 한다.
- 실제 백엔드와 붙이는 확인은 하지 않았다(7단계 전). 프록시 설정과 계약 준수는 7단계 뒤에 확인한다.
- "내 요청"과 결재함은 화면을 열 때 한 번 불러오고 자동으로 갱신하지 않는다(새 요청은 화면을 다시 열면 보인다).
- 화면 자동 테스트는 순수 함수와 스트림 흐름만 있다. 컴포넌트 화면은 브라우저로 직접 확인했고 스크린샷 파일은 남기지 않았다.
- `docs/handoff/feedback_web.md`(리뷰어 파일)는 worktree에 추적하지 않은 채로 있다.
