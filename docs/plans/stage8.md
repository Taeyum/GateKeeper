# 8단계 계획: 화면 (백엔드와 병렬)

## Context

백엔드(5~7단계)가 아직 없는 상태에서 화면(`web/`)을 먼저 만든다. 둘이 어긋나지 않도록 응답 JSON 모양을 `docs/API_CONTRACT.md`로 먼저 정하고(확정, 747464c), 화면은 그 계약대로 만든 Vite 목업으로 개발한다. 7단계가 끝나면 목업을 끄고 실제 API에 붙인다.

- 작업 위치: git worktree `../skala-aiagent-web`, 브랜치 `feat/web`(main `ce12f3c`에서 분기). 메인 세션의 5단계와 파일이 겹치지 않는다.
- 디자인: https://claude.ai/artifact/8W4pp3cmUCZP6cRXdAhe35 (artboard 4개). 결재 업무 화면이고 채팅 화면이 아니다.

## 사용자 결정

| 항목 | 결정 |
|---|---|
| schemas.py | 바꾸지 않는다. 화면에 필요한 값은 상세 응답의 선택 필드로 더한다 |
| 조건부 대안 | `conditional_alternative`(문장)는 그대로. 상세 응답의 선택 필드 `alternative_diff`가 있으면 "지금 → 이렇게" 비교, 없으면 문장만 |
| 상세 응답 | `structured`, `impact`, `similar_incidents[]`. 이름은 데이터 파일의 원래 키 |
| 규정 문구 | 화면에 rule_id → 쉬운 문구와 묶음 매핑 표(CHG-01~10 전부). 엔진 근거 문장은 "자세한 근거"에 그대로, 모르는 rule_id는 엔진 문장으로 대신 |
| 건너뛴 노드 | 서버는 실행한 노드의 이벤트만 보낸다. 시작하지 않은 노드는 화면이 표시한다(정상 종료면 "건너뜀", `error`/수동 검토면 "진행 안 됨") |
| 목업 데이터 | `requests_dev.json`, `cmdb.json`, `change_calendar.json`, `open_incidents.json`, `history.json`만. eval 폴더의 다른 파일은 읽지 않는다 |
| 리뷰 결정 | `docs/handoff/feedback_web.md`의 열린 질문 9개와 L1~L4를 계약에 반영(재요청은 `parent_request_id`로 새 요청, 내 요청 목록 `GET /api/requests`, 서브그래프 내부 노드는 안 보냄, 수동 검토는 `done`+`message`) |

## 수정 범위

수정하는 파일: `web/`, `docs/API_CONTRACT.md`, `sh/run_web.sh`, `docs/plans/stage8.md`, `docs/reports/stage8.md`. 그 밖(`app/`, `tests/`, `docs/PROGRESS.md`)은 건드리지 않는다. 결과는 `docs/reports/stage8.md`에 쓰고, PROGRESS.md 갱신은 메인 세션이 머지 후 한다. 커밋 메시지에는 AI 출처 문구를 넣지 않는다.

## 디자인 정리 (artboard별 구성과 상태)

| 화면 | 구성 | 상태 (디자인에 있는 것 / 이번에 더하는 것) |
|---|---|---|
| 1. 요청자 작성 | 밴드 헤더(메뉴, 역할 전환), 입력창, 유형별 안내 탭 4개(방화벽/배포/DB/자동 승인 대상), 제출 버튼, "내 요청" 목록(`GET /api/requests`) | 있음: 빈 입력, 목록 상태 4종(승인자 확인 중/승인됨/자동 승인/조건부 승인). 추가: 제출 중, 입력 검증 오류, 목록이 비었을 때, 재요청(고쳐 쓰기)에서 본문 미리 채움 |
| 2. 요청자 검토 진행 중 | 8단계 타임라인(③은 세 갈래 병렬), "내가 쓴 내용", "이렇게 이해했어요"(빠진 항목 표시), 단계 설명 접기 | 있음: 완료/확인 중/대기. 추가: 건너뜀, 진행 안 됨, 확인 못 했어요(부분 실패), 스트림이 끊겨 상태를 다시 읽는 중, 수동 검토로 넘김(`done`+`message` 또는 `error`) |
| 3. 요청자 결과 | 판정 요약(배지, 한 줄 결론, 위험도/비슷한 사고/상태 칩), "이렇게 고쳐 주세요" 묶음과 다시 요청 버튼, 자세한 근거(접힘), 비슷한 사고 카드, 처리 상태 | 있음: 반려 권고. 추가: 조건부 승인, 승인, 자동 승인 변형, 긴급 변경(사후 보고 안내), `alternative_diff` 없음(문장만), 비슷한 사고 없음(카드 숨김), 승인자 결정 후(승인됨/반려됨 표시) |
| 4. 승인자 결재함 | 밴드 안 탭(결재 대기/자동 승인 기록), 목록(요청/시스템 권고/위험도), 상세 패널(요약, 이유, 영향 범위, 비슷한 사고, 제안한 대안, 원문과 규정 근거 접힘, 결정 사유와 승인/반려) | 있음: 반려 권고 행 선택. 추가: 행 선택에 따른 상세 전환, 비었을 때, 결정 보내는 중과 완료, 403 |

디자인 속 예시 데이터(결재함 6건, 요청 번호, "order-service 새 버전 배포 (v3.2)" 같은 이름)는 가상이다. 화면은 데이터에서 만든다(요청 이름은 `target`과 `change_type`으로).

## 순서

1. **계약**(완료): `docs/API_CONTRACT.md` 확정, 별도 커밋(747464c).
2. **앱 뼈대**: `web/`에 Vue 3 + Vite + TypeScript + Vue Router. `web/src/api/types.ts`는 계약과 1:1. 역할(요청자 김운영/승인자 박CAB)은 상단 전환으로 정하고, fetch 래퍼가 `X-User-Role`, `X-User-Name`(퍼센트 인코딩)을 붙인다. 디자인 토큰(색, 글꼴, 둥근 정도)은 디자인에서 옮긴다. `sh/run_web.sh`.
3. **목업**: Vite 개발 서버 미들웨어(`web/mock/`)가 `VITE_API_MOCK=1`일 때만 `/api`를 흉내 낸다.
   - 요청 3건 시나리오: REQ-D01(반려, 8노드, 병렬 3개의 완료 시점이 다름), REQ-D03(조건부 승인, 비슷한 사고 HIS-034), REQ-D04(표준 변경, 자동 승인, impact/history/validate 건너뜀). 수동 검토(`done` + `manual_review`) 시나리오 1건을 더해 "진행 안 됨" 표시를 확인한다.
   - 결재함과 내 요청 목록(`GET /api/requests`, `GET /api/approvals`)은 `requests_dev.json`의 `expected`(verdict, risk)로 채운다. `has_similar_incident`는 계약의 정의(같은 서비스 + 같은 유형 + `outcome` 장애)로 `history.json`에서 계산한다. 자동 승인 기록은 표준 변경 요청에서 만든다.
   - 새 요청(`POST /api/requests`)은 위 시나리오 중 입력 문장에 맞는 것을 고르고, `parent_request_id`가 오면 새 `request_id`로 부모의 결과를 고친 형태(재요청)를 돌려준다.
   - `alternative_diff`는 REQ-D01만 값을 주고 나머지는 `null`로 둬서 "문장만" 경로를 확인한다.
   - 근거 문장(evidence)은 규칙 엔진을 한 번 돌려 얻은 실제 문장을 고정 파일로 옮긴다(실행용 스크립트는 커밋하지 않는다).
   - 스트림 끊김 복구: `VITE_MOCK_DROP=1`이면 세 번째 이벤트 뒤 연결을 끊어 `GET /api/requests/{id}` 복구 경로를 확인한다. 연결하면 지난 이벤트를 replay한다.
   - decision은 상태를 바꾸고 결재함 목록에 반영한다.
4. **요청자 화면**: 작성, 진행 타임라인(상태 계산은 계약의 "건너뜀 규칙"대로 순수 함수로 분리), 결과 카드, 재요청(`parent_request_id`).
5. **승인자 화면**: 탭, 목록, 상세, 결정.
6. **실제 연결**: `VITE_API_MOCK`을 끄면 Vite 프록시로 `/api`를 `localhost:8000`에 보낸다. 7단계가 끝난 뒤에만 확인한다.

## 규정 문구 매핑 표

화면 쪽 `web/src/copy/rules.ts`에 둔다. 말투는 "~해요"로 디자인과 같다. 엔진 문장은 모든 줄의 "자세한 근거"에 그대로 보여 준다.

| 묶음(결과 화면 제목) | rule_id | 쉬운 문구 |
|---|---|---|
| 작업 시간을 바꿔 주세요 | CHG-01 | 금요일 저녁부터 월요일 아침까지는 변경할 수 없어요. |
| 작업 시간을 바꿔 주세요 | CHG-06 | 같은 서비스에 같은 시간대 작업이 이미 있어요. |
| 작업 시간을 바꿔 주세요 | CHG-10 | 월말 정산이나 대형 행사처럼 변경이 막힌 기간이에요. |
| 접속할 곳을 정해 주세요 | CHG-02 | 접속할 곳(IP)을 정하지 않으면 누구나 접속할 수 있는 상태로 봐요. |
| 접속할 곳을 정해 주세요 | CHG-03 | DB 포트는 외부에 열 수 없어요. 등록된 파트너 IP 1개(/32)만 예외예요. |
| 열어 둘 기간을 적어 주세요 | CHG-09 | 외부 접속을 열 때는 기간(최대 30일)을 정해야 해요. |
| 되돌리는 방법을 적어 주세요 | CHG-04 | 문제가 생기면 되돌릴 방법(롤백 계획)을 적어 주세요. |
| 테스트 결과를 붙여 주세요 | CHG-08 | 운영에 반영하기 전에 테스트 서버에서 확인한 결과를 붙여 주세요. |
| 더 일찍 요청해 주세요 | CHG-05 | 핵심 서비스는 작업 24시간 전까지 요청해야 해요. |
| (긴급 변경 안내) | CHG-07 | 긴급 변경은 열려 있는 장애 티켓이 필요하고, 24시간 안에 사후 보고를 해야 해요. |

규칙: 매핑에 없는 rule_id는 묶음 "그 밖의 확인할 것"에 엔진 문장을 그대로 넣는다. 한 묶음의 "지금 → 이렇게" 비교는 `alternative_diff`의 `field`가 `start`/`end`(작업 시간), `source`(접속할 곳), `expires_days`/`expires_at`(열어 둘 기간)일 때만 붙고, 그 밖의 묶음은 문구만 보여 준다.

## 확인 방법

1. 순수 함수 단위 테스트(Vitest): 노드 상태 계산(대기/확인 중/완료/건너뜀/진행 안 됨/확인 못 했어요, v1과 표준 변경 경로, `error`와 수동 검토 종료), 규정 매핑이 CHG-01~10을 모두 덮는지와 모르는 rule_id 대체, 이벤트를 상태로 접는 함수, 헤더 이름 인코딩.
2. 목업 서버를 띄워 직접 확인: 요청 작성 → 진행 타임라인 → 반려 결과 → 재요청 → 역할 전환 → 승인자 결재함에서 반려 처리까지. 표준 변경(건너뜀), 수동 검토(진행 안 됨), `VITE_MOCK_DROP=1`(복구)도 본다. 화면은 브라우저로 열어 스크린샷을 같이 남긴다.
3. 시연 순서와 커밋 분할 목록은 `docs/reports/stage8.md`에 쓴다.

## 보고서에 적을 것

- 한계: 쉬운 문구의 숫자(30일, 24시간)는 화면에 고정된 규정 값이다. 규정(`rules.json`)이 바뀌면 화면 문구도 고쳐야 한다.
- 메인으로 가져갈 때: 7단계 프롬프트의 재요청 항목을 "`parent_request_id`로 새 요청을 만든다"로 바꿔 넣는다(`docs/API_CONTRACT.md` 1장).
