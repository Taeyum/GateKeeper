# 5분 시연 (발표용)

시나리오는 [REPORT 4장](REPORT.md#4-시연-시나리오)과 같고, 2026-10-22에 실제 서버(Claude Sonnet 5.5, v2)와 화면으로 리허설해 확인한 값만 적었다. 리허설 기록과 함정은 3장에 있다.

## 1. 발표 전 준비 (10분 전)

```bash
# 터미널 1: Ollama (이력 RAG 임베딩 bge-m3에 필요. 이미 떠 있으면 생략)
ollama serve
# 터미널 2: API (v2, 포트 8100). 과금 확인 프롬프트에 y
LLM_PROVIDER=anthropic bash sh/run_api.sh
# 터미널 3: 화면 (http://127.0.0.1:5173)
bash sh/run_web.sh
```

- 이력 색인이 없으면 API가 안 뜨고 이유를 알려 준다. `bash sh/build_index.sh`(약 20초)를 먼저 한다.
- 브라우저는 폭 1440 전후, 확대 100%로 연다. 역할은 브라우저에 저장되므로 **요청자 김운영**으로 시작하는지 확인한다.
- 요청 목록을 비우려면 서버를 끄고 `.data/checkpoints.sqlite*`와 `.data/audit.jsonl`을 지운 뒤 다시 띄운다. 리허설은 `GK_CHECKPOINT_DB=.data/rehearsal/checkpoints.sqlite GK_AUDIT_LOG=.data/rehearsal/audit.jsonl`로 경로를 따로 줘서 기존 데이터를 건드리지 않았다.
- 한 건을 미리 돌려 본다(약 0.07 USD). 서버와 키, 임베딩이 이어지는지 보는 가장 확실한 방법이다.
- (선택) 결재함에 다른 요청이 있으면 "위험도 높은 순" 설명이 살아난다. 요청자 화면에서 아래를 미리 제출해 둔다(요청자 이름은 모두 김운영으로 보인다). 리허설에서는 다른 이름으로 넣어 이 세 건이 각각 승인(높음), 승인(중간), 반려(낮음)로 나왔다.
  - `내일 오후 3시에 auth-db max_connections를 200에서 300으로 늘릴게요. 롤백은 설정을 원래대로 되돌리는 것이고 스테이징 테스트 결과는 첨부했어요.`
  - `내일 오후 2시에 order-service 새 버전을 배포할게요. 롤백은 이전 이미지로 되돌리고, 테스트 결과도 첨부했어요.`
  - `이번 주 토요일 새벽 2시에 admin-portal 방화벽을 열어서 재택 운영팀이 접속할 수 있게 해주세요.`

**날짜 주의.** 시연 문장의 "10월 30일 금요일"은 동결 기간 FRZ-01(10/30 00:00 ~ 11/2 09:00, payments-db 포함)과 금요일 저녁에 걸려 CHG-10과 CHG-01이 나오도록 고른 날짜다. 발표가 10/30 이전이어야 한다. 아래 표는 `change_calendar.json`과 규정에서 계산한 것이고, 리허설은 10/22에만 했다.

| 발표 날짜 | 첫 문장 | 고쳐 쓰기 문장의 일정 |
|---|---|---|
| ~ 10/29 | `10월 30일 금요일 저녁 8시에 ...` | `11/3 화요일 오후 2시` |
| 10/30 ~ 11/5 | `11월 6일 금요일 저녁 8시에 ...` (동결 FRZ-02 11/6 ~ 11/9, 전 서비스) | `11/10 화요일 오후 2시` |

고쳐 쓰는 일정은 동결 밖이고 요청 시각에서 24시간 이상 뒤여야 한다(Tier-1 사전 공지, CHG-05). 결과 화면의 "이렇게" 카드가 그 날짜를 알려 준다.

## 2. 5분 순서

| 시간 | 화면 | 하는 일 | 말할 포인트 |
|---|---|---|---|
| 0:00 ~ 0:30 | (슬라이드) | 문제 한 줄과 원칙 | 변경관리자는 규정, CMDB, 일정, 장애 이력을 네 화면에서 맞춰 보며 위반을 찾는다. **판정은 코드가 하고 LLM은 해석과 설명만 한다.** 최종 결정은 사람이다. |
| 0:30 ~ 1:30 | 요청 작성, 진행 화면 | 요청자 김운영으로 `10월 30일 금요일 저녁 8시에 payments-db 방화벽 좀 열어주세요. 외부 파트너사가 접속해야 해요.`를 입력하고 "검토 요청하기" | 진행 화면에서 말한다(검토는 20~30초). 규정 확인, 영향 확인, 사고 사례 확인 **세 갈래가 동시에** 돈다. "이렇게 이해했어요"에서 시스템이 접속할 곳과 열어 둘 기간이 **빠졌다**고 먼저 짚는다. |
| 1:30 ~ 2:30 | 결과: 반려 권고 | 반려 권고, 고칠 것 3가지, "지금 → 이렇게", "자세한 근거 보기"를 펼친다 | 걸린 규정은 5개다: 금요일 저녁(CHG-01), 동결 기간(CHG-10), 전체 오픈(CHG-02), DB 포트 외부 노출(CHG-03), 기한 없음(CHG-09). **이 판정은 LLM이 아니라 규칙 엔진이 낸 것**이라 같은 요청은 늘 같은 결과다. 비슷한 사고(파트너 임시 허용 후 결제 승인 지연)는 위험도만 올리고 판정은 안 바꾼다. |

## 3. 리허설 기록 (2026-10-22)

실제 서버(`LLM_PROVIDER=anthropic bash sh/run_api.sh`)와 화면(`bash sh/run_web.sh`)을 브라우저 자동화로 조작해 두 번 돌렸다. 브라우저 콘솔 오류는 0건이었다.

| 단계 | 소요 | 결과 |
|---|---|---|
| 시연 문장 검토 | 30.9초(1회차), 21.7초(2회차) | 반려 권고, 위험도 높음, 비슷한 사고 있음, 걸린 규정 5개(CHG-01/02/03/09/10), 고칠 것 3가지 |
| 승인자 반려 처리 | 0.5초 | 요청자 화면에 "반려됐어요"와 코멘트 |
| 원클릭 "이 내용으로 다시 요청하기" | 17.1초 | **다시 반려 권고**(걸린 규정 CHG-02/03, 고칠 것 1가지) |
| 직접 고쳐 쓰기 재요청 | 측정 못 함 | 승인, 규정에 어긋나는 곳 없음. 승인자가 사유 없이 승인(0.4초). 소요는 대기 조건을 잘못 써서 재지 못했다(같은 경로의 원클릭은 17.1초) |
| 표준 변경(시각 포함) | 20.4초 | "자동으로 승인됐어요", 승인자 "자동 승인 기록" 탭에 쌓임 |

리허설에서 **문서와 달랐던 것 세 가지**(이 문서와 REPORT 4장에 반영함)

1. 원클릭 재요청은 다시 반려된다. 보내는 문장의 접속할 곳이 "등록된 파트너 IP"라는 문구라서 엔진이 출발지를 못 읽는다. 목업(`VITE_API_MOCK=1`)은 이 경우 승인으로 끝나서 실제와 다르다. 향후 개선 후보다(REPORT 6.2의 6번).
2. 작업 시각이 없는 표준 변경은 자동 승인되지 않고 조건부 승인이 나온다. 화면에는 "작업 시각이 없어 시간 조항을 확인하지 못했다"와 함께 "근거 검증 미완료" 경고도 보인다.
3. 시스템이 반려를 권고한 요청을 승인하려면 사유를 적어야 한다(권고와 다르게 결정할 때 사유 필수).

검토 시간은 매번 다르다(같은 문장이 21.7초, 30.9초). 30초를 넘겨도 정상이고, 그 시간에 설명을 이어 가면 된다. 결과 문장과 "이렇게" 카드의 일정(10/23 오전 10시, 오후 2시 등)은 실행마다 조금 달라질 수 있다. Claude 5.5는 temperature를 고정할 수 없다.

## 4. 문제가 생기면

- **API가 느리거나 응답이 없다**: 진행 화면에 머무르며 설명을 이어 간다. 안 되면 슬라이드의 화면 이미지로 넘어간다.
- **키나 네트워크 문제**: `VITE_API_MOCK=1 bash sh/run_web.sh`로 목업 화면을 띄운다(백엔드 불필요). 순서는 [stage8 보고서](reports/stage8.md)에 있다. 단 목업은 위 1번처럼 재요청이 승인으로 끝난다.
- **서버를 껐다 켰다**: 승인 대기 요청은 SQLite 체크포인터에 남아 있어 다시 띄운 뒤에도 결재함에 보인다(7단계에서 강제 종료로 확인).
- **"이대로는 승인되기 어려워요"가 안 나오고 규정이 안 걸린다**: 날짜 문제다. 1장의 날짜 표를 본다.

## 5. 예상 질문

| 질문 | 답 |
|---|---|
| 왜 LLM이 아니라 규칙 엔진이 판정하나? | 판정은 일관성과 감사 가능성이 필요하다. 작은 모델은 LLM 단독일 때 판정의 35.0%만 맞혔고, 판정을 코드로 옮긴 v1은 75.0%였다. 판정이 자기 위반 목록과 모순되는 일도 15.0%에서 0%가 됐다. |
| 강한 모델이면 LLM 단독으로 충분하지 않나? | Sonnet은 v0도 판정 100%였다. 구조가 더한 것은 이력 기반 위험도(88.9% → 100%)와 조항별 근거, 감사 로그다. 대가로 지연이 79%, 요청당 비용이 54%(0.044 → 0.068 USD) 늘었다. |
| 구조화가 틀리면? | 엔진은 틀린 입력도 정확히 판정한다. 로컬 모델에서 시각 구조화 정확도가 25~45%였다. 완화책은 자동 승인을 표준 경로에서만 하는 것과 시각이 없으면 표준으로 확정하지 않는 것이고, 원문 날짜와 대조하는 방어는 향후 과제다. |
| 규정이 바뀌면? | 시간대, 포트, 기한 같은 값은 `rules.json`과 규정 원문(MCP Resource)에서 읽는다. 화면 문구의 숫자(30일, 24시간)는 화면에 고정돼 있어 같이 고쳐야 한다. |
| 평가를 믿을 수 있나? | eval 정답은 개발 중 보지 않았고 한 번만 쟀다. 여섯 실행 모두 clean 커밋(f8abcf0)이고 측정 뒤 코드를 고치지 않았다. 로컬 모델 축은 Sonnet 포화를 본 뒤 더한 사후 축이라는 것도 밝혔다. 20건이라 통계적 결론은 아니다. |
