# 최종 평가 결과 (9단계)

eval 20건으로 v0, v1, v2를 한 번씩 측정한 결과다. 측정 설계와 지표 정의는 `docs/EVAL.md`, 원자료는 `results/*_eval.summary.json`, 자동 생성 리포트와 차트는 `results/report_eval_anthropic.md`, `results/report_eval_ollama.md`와 `results/charts_eval_*/`이다. 아래 수치는 모두 summary.json에서 옮겼고, 정답 파일(`requests_eval.json`, `label_review.md`)은 읽지 않았다(CLAUDE.md 절대 규칙 1). 그래서 오답이 된 개별 사례의 원인은 집계로만 따졌고, 사례 단위로 확인하지 못한 것은 "추정"이라고 적었다.

## 1. 한눈에 보기

1. **강한 모델(Sonnet 5.5): 정확도로는 구조의 효과가 안 보인다.** v0, v1, v2 모두 판정 정확도 100%(60/60), 일관성 100%다. v1과 v2는 위반 정밀도(100.0% → 95.0%)와 대안 품질(4.85 → 4.51 / 4.59)이 오히려 낮고, 지연 평균은 +37% / +79%, 요청당 비용은 +10% / +54% 늘었다. 구조가 만든 뚜렷한 이득은 v2의 위험도 일치율 88.9% → 100.0% 하나다.
2. **약한 모델(qwen3:4b): 구조가 정확도를 크게 올린다.** 판정 정확도가 v0 35.0%에서 v1 75.0%로 오른다. 대가는 지연 평균 10.3초 → 62.3초(약 6배), LLM 호출 1.00회 → 5.05회다. v2는 v1보다 나아지지 않았다(70.0%, 오류 2건).
3. **dev와 같은 방향이다.** dev에서 본 패턴(Sonnet은 포화, qwen3:4b는 v0 40% → v1 80%)이 eval에서도 나왔다. 다만 v1과 v2의 위반 정밀도 95.0%(오인용 3건)는 dev에서 안 보이던 약점이다.
4. 두 축의 수치는 모델이 달라 서로 비교하지 않는다. 축 선택이 사후에 이뤄진 점은 6장에 적었다.

**숫자 표기와 반올림 규칙**

- 값은 summary.json의 원값을 그대로 쓰고 `eval/report.py`와 같은 규칙으로 표시한다(파이썬 `f"{x:.1f}"` 반올림).
- 비율(정확도, 정밀도, 재현율, F1, 일관성, 자기모순, 위험도 일치율)은 원값(0~1)에 100을 곱해 소수 첫째 자리까지 쓴다.
- 변화 "%p"는 표시된 반올림값끼리 뺀 것이 아니라 원값의 차를 구한 뒤 반올림한다.
- 지연은 초, 소수 첫째 자리. 토큰은 정수에 천 단위 쉼표. LLM 호출 수와 대안 품질은 소수 둘째 자리. 요청당 비용은 USD 소수 다섯째 자리, 합계 비용은 소수 둘째 자리.
- 상대 변화(%)는 원값 비율을 정수로 반올림한다.
- p95는 nearest-rank다. 실행이 60건이면 57번째, 20건이면 19번째 값이다.
- 원값에서 계산한 파생값은 "계산값"이라고 표시했다.

## 6. 사후에 추가된 축과 dev에서 정한 것

이 평가의 축은 처음부터 정해 둔 것이 아니다. 순서는 다음과 같다.

1. 처음 설계는 버전(v0, v1, v2) 하나가 비교 축이었고 모델은 Sonnet이었다.
2. 5단계 dev에서 Sonnet의 v0와 v1이 모두 100%로 갈리지 않았다. EVAL.md 6장대로 정답셋과 v0 프롬프트는 바꾸지 않고, 약한 모델 축(Haiku)을 더했다. Haiku에서도 v0와 v1이 모두 100%였다.
3. 그다음 외부 API를 못 쓰는 환경을 가정한 로컬 모델 축(qwen3:4b)을 더했다. 여기서 처음으로 구조의 효과가 정확도에 나타났다(dev v0 40% → v1 80%).
4. 최종 평가는 Sonnet(주 축)과 qwen3:4b(로컬 모델 축) 두 축으로 쟀다. Haiku 축은 dev에서만 쟀고 이번 단계의 지시로 최종 평가에서는 제외했다.

따라서 **모델 축과 로컬 모델 축은 둘 다 dev 결과를 본 뒤에 추가한 사후 축이다.** 구조의 효과가 보이지 않는 결과를 확인한 뒤 효과가 보일 만한 모델을 더한 것이므로, qwen3:4b 축의 큰 개선폭(+40.0%p)을 "구조 일반의 효과"로 읽으면 안 된다. 이 모델은 v0 단독으로는 판정의 35.0%만 맞히는 모델이라서 구조의 효과가 가장 크게 나오는 조건이다.

다만 두 가지는 지켰다. 첫째, 축은 eval 정답이나 결과를 보기 전에 정했다(eval은 이 단계에서 처음 실행했다). 둘째, qwen3:4b는 정확도가 아니라 이 PC의 VRAM 6GB에 전부 올라가는 크기(`num_ctx=10240`에서 100% GPU)라는 이유로 골랐다(EVAL.md 1장). 따라서 eval 20건의 결과는 dev에서 고른 축이 새 데이터에서도 재현되는지에 대한 확인이다.

## 8. 한계와 트레이드오프

**개선이 새로 만든 약점**

- v1은 호출이 4.55배(Sonnet)로 늘어 지연과 비용이 늘었다. 병렬 서브에이전트를 썼는데도 Sonnet 축에서 v1의 지연(평균 14.2초)이 v0(10.4초)보다 길다. 단계가 여러 개라 직렬로 이어지는 부분(구조화, 분류, 결정)이 병렬의 이득을 넘는 것으로 보이나 이 평가는 단계별 지연을 분해하지 않았다.
- v1과 v2는 구조화한 값을 엔진에 넣어 판정하므로 구조화 오류를 그대로 위반 목록에 옮긴다(아래 1번).
- v2는 지연과 비용을 늘린다. 근거를 더하는 대신 v0 대비 Sonnet 요청 하나가 평균 10.4초에서 18.6초로, 0.044 USD에서 0.068 USD로 늘었다.
- 로컬 모델에서는 v2가 600초 제한에 걸린 요청을 만들었다(TimeoutError 1건).

**1. 구조화 오류가 판정 오류로 이어진다.** 규칙 엔진은 입력이 맞아야 맞게 판정한다. qwen3:4b에서 start와 end 정확도는 v0 45.0%, v1 30.0%, v2 25.0%(9/20, 6/20, 5/20)다. 엔진은 틀린 시각을 정확히 판정하므로 시간 조항(CHG-01, 05, 06, 10)의 판단이 흔들린다. 그래서 v1의 구조화 정확도(83.7%)는 v0(88.6%)보다 낮은데도 판정 정확도는 v0의 두 배를 넘는다(75.0% 대 35.0%). 구조가 정확도를 올리는 이유는 구조화를 더 잘해서가 아니라 판정을 LLM이 아니라 코드가 하기 때문이다. 구조화는 오히려 약점으로 남는다. Sonnet 축에서도 expires_at 57/60(v1, v2)과 source 57/60(v1)이 100%가 아니었고, v1과 v2의 위반 정밀도 95.0%(오탐 3건)와 크기가 맞는다. 오탐 3은 반복 횟수와 같아서 한 요청이 3회 같은 오류를 낸 값과 맞지만, 원인이 expires_at 구조화 오류인지는 사례 단위로 확인하지 못했다(추정). 정답 파일을 열어야 하는 확인이라 하지 않았다. 이 오탐은 판정을 바꾸지 않았다(판정 100%). 구조화를 정확히 읽는 능력이 이 시스템의 가장 약한 고리다.

**2. 잘못된 자동 승인과 K3.** 측정 지점이 approval_gate 직전이라 7단계의 K3(자동 승인은 route가 standard일 때만)는 평가에 들어 있지 않다. dev의 qwen3:4b에서 REQ-D10(정답 반려, 예측 자동 승인)은 시각 구조화 오류로 동결(CHG-10)을 못 잡아 자동 승인이 나왔다. 제품 경로에서는 이 요청에 분류 불일치 경고가 붙어 route가 general이 되므로 K3가 사람에게 보낸다. 이 방어는 분류 모델(qwen3:0.6b)이 구조화와 다르게 판단할 때만 동작하고, 두 모델이 같은 방향으로 틀리면 막지 못한다. eval에서 분류 불일치 경고는 qwen3:4b의 v1과 v2에서 각 3건, Sonnet에서는 0건이었다. 그중 몇 건이 잘못된 자동 승인이었는지는 summary로는 알 수 없다. 즉 이 평가의 qwen3:4b 판정 정확도는 K3를 적용하기 전 값이고 제품이 사람에게 넘기는 오류는 이보다 적을 수 있지만, 구조화 시각과 원문의 날짜 표현을 대조하는 방어는 아직 없다(PROGRESS 남은 이슈).

**3. 강한 모델에서는 정확도가 포화한다.** Sonnet은 v0 단독으로도 판정 100%, 위반 F1 100%, 일관성 100%다. 판정 정확도와 일관성으로는 구조의 효과를 가를 수 없다(EVAL.md 6장의 경우). 이 모델에서 구조가 남기는 것은 위험도(v2)와 판정 근거를 코드로 추적할 수 있다는 점이고, 비용으로는 지연, 토큰, 호출 수가 늘고 위반 정밀도와 대안 품질이 오히려 낮았다. 이 결과는 "모델이 충분히 강하면 규정을 통째로 넣은 단독 호출로 충분하다"는 읽기와 양립한다. 한편 이 평가는 v0에도 규정, CMDB, 캘린더, 티켓을 전부 줬다(공정성 장치). 실제 사내 규정이 이 데이터보다 훨씬 크고 변경이 잦다면 통째로 넣는 방식이 한계에 닿을 수 있는데, 이 평가는 그 상황을 검증하지 않았다.

**4. 표본이 작다.** 요청 20건, Sonnet은 3회, qwen3:4b는 1회다. 판정 정확도 5.0%p는 qwen3:4b에서 한 건 차이다. 수치 차이를 통계적 결론으로 읽지 않는다. Anthropic은 temperature를 보내지 않아 같은 요청의 결과가 실행마다 달라질 수 있는데, 일관성 100%(20건 모두 3회 같은 판정)는 판정에 대해서만 안심시킨다. 위반 목록이나 설명의 변동은 이 지표가 보지 않는다.

**5. 오류와 환경.** qwen3:4b v2에서 오류 2건(TimeoutError 1, ReviewIncomplete 1)이 나왔다. 오류는 모든 지표에서 오답으로 세는 규칙대로 기록했고 재측정하지 않았다(결과를 본 뒤 다시 재면 고르는 것이 된다). 두 오류의 원인은 분석하지 않았다. 지연은 이 PC(GTX 1660 SUPER, VRAM 6GB, 단일 Ollama 서버)의 값이라 환경에 의존한다. Ollama 서버가 요청을 한 건씩 처리하면 v1의 병렬 호출이 줄을 서서 병렬의 이득이 이 축에서는 보이지 않는다.

**6. 비용은 추정이다.** 토큰 x 단가이고 캐시 할인과 warm-up은 반영하지 않았다. thinking 토큰은 출력 토큰에 포함된다. Judge 비용(5.21 USD)은 시스템 비용과 따로 센다.

**7. 이 측정은 한 번뿐인 held-out 측정이다.** eval 정답 파일을 저장소에 공개했으므로 이 결과를 본 뒤 프롬프트나 로직을 고치면 같은 eval로 다시 잰 값은 held-out이 아니다. 고친다면 새 정답셋이 필요하다.

**재검토 조건과 제안(구현하지 않음)**

- Sonnet 급 모델에서 v2의 지연 +79%와 비용 +54%가 사 주는 것은 위험도 +11.1%p뿐이다. 지연 SLA가 있다면 Validator를 반려/조건부 판정에만 적용하거나, 이력 상향(결정론)만 남기고 검증 LLM 호출을 줄이는 방안을 검토한다.
- 약한 모델에서는 v1까지가 이득이고 v2는 이 측정에서 이득이 없다. 로컬 환경 배포가 목표라면 v1을 기본으로 하고, 지연(평균 62.3초)이 문제면 구조화 단계를 더 강한 모델에 맡기는 구성을 검토한다.
- 구조화 정확도가 시스템의 상한을 정하므로, 구조화 시각과 원문의 날짜 표현을 대조하는 방어(PROGRESS 남은 이슈)를 다음 후보로 둔다.
- v1과 v2의 위반 정밀도 95.0%는 정답을 아는 사람이 사례 단위로 원인을 확인해야 한다(구조화 오류인지, 엔진과 라벨의 해석 차이인지).

## 9. 측정 후 수정

**없다.** 측정을 시작한 뒤(`f8abcf0`)에는 코드, 프롬프트, 단가표, 정답을 바꾸지 않았고 여섯 실행 모두 같은 clean 커밋에서 돌았다. 측정 전 준비에서 정한 것은 버그 수정이 아니라 실행 방식이다: 결과를 `.data/final_eval`에 쓴 것(dirty 표시 방지), qwen3:0.6b 단가를 0으로 둔 것(로컬 축의 비용 칸이 "-"가 되지 않게). qwen3:4b v2의 오류 2건은 버그 수정 대상으로 보지 않고 측정된 행동으로 기록했다. 이후 버그를 발견해 고치면 이 절에 "측정 후 수정"으로 적고 새 정답셋으로 다시 잰다.

측정 후 수정(API 재요청 경로, 평가 그래프 영향 없음): 재요청의 재요청에서 부모의 새로 쓴 본문만 `[이전 요청]`으로 넣어 원 요청의 대상이 빠지던 것을, 부모의 그래프 입력(`masked_text`)을 쓰도록 고쳤다(`app/api/routes.py`). 평가 하네스는 이 경로를 거치지 않아 재측정하지 않았다.
